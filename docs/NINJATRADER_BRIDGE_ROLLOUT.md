# NinjaTrader multi-account bridge rollout

This checklist describes the local release candidate. It is not evidence that the hosted API, database, frontend, or NinjaTrader PC has been updated. No production schema or data change is authorized by this document.

## Release gate and backup

1. Identify the actual hosted API deployment, frontend deployment, database provider, and private attachment storage. The repository has Supabase/PostgreSQL support and a hosted API URL in the bridge helper, but it does not contain a verified production deployment or restore procedure.
2. Record the current deployed backend/frontend revisions and `alembic_version`. Confirm the database is at `0015` before applying `0016`; investigate any other version instead of stamping it. Confirm the frontend API origin matches the API being upgraded.
3. Create a provider-native, restorable database backup or snapshot and a private storage backup. Include broker connections/events, imports, trades, journals, screenshots, attachments, reviews, analytics inputs, and intelligence records. The in-app ZIP is a useful extra export, but it is not a database restore image and omits some tables.
4. Restore the backup to an isolated target and verify schema version, critical table counts, representative trade/journal/attachment records, and attachment bytes. Record the restore method, operator, backup identifier, and rollback window without recording credentials.
5. Obtain explicit approval before touching production data or applying `0016`. Never print or save bridge keys in release logs.

## Migration and staged release

Revision `0016` depends on `0015`. It adds nullable `installation_id`, `source_namespace`, and `source_account_name` columns to `broker_connections`, a self-reference with `ON DELETE SET NULL`, an index, and a unique constraint on the installation/source pair. It contains no UPDATE, DELETE, or trade-table DDL. Existing rows keep null source fields. Do not run its downgrade as routine rollback: after new source records exist, dropping these fields would erase their mapping identity.

**Do not deploy the new backend before the backup gate and approval.** `backend/app/main.py` runs `alembic upgrade head` during application startup, so starting a new backend build against production would apply `0016` automatically. After approval, apply `0016` to the identified database and verify `alembic_version = 0016`; then deploy the matching backend and frontend and check health plus the authenticated Connections page before changing the NinjaTrader PC. Keep the legacy connector available during this check. If the application release fails before switching the AddOn, restore the previous application revisions while leaving the additive schema in place; investigate before considering any schema rollback.

Record before/after counts for `broker_connections`, `broker_execution_events`, `trades`, `trade_journals`, `attachments`, `capture_events`, and `import_sessions`, plus a sampled account mapping and attachment read. The migration itself should not change those counts or existing row IDs.

## Windows AddOn cutover

1. While the old connector still works, check `%USERPROFILE%\Documents\JournalMe\bridge-queue.txt` and `bridge-queue-v2.txt` for pending lines **without opening or printing their contents**. A nonempty old queue must drain under its old single-account key and `account_name`. If v2 exists, the updated AddOn can run temporarily with that same old configuration to drain it. Do not delete either queue.
2. Wait until the affected positions are flat and both queues are empty. Existing legacy and new source connections reconstruct trades independently; switching during an open position or replaying the same session can produce split or overlapping trades.
3. On **Settings → Broker Connections**, add one NinjaTrader installation and generate its one-time key. On the NinjaTrader PC, run `integrations\ninjatrader\configure_bridge.ps1` without `-AccountName`; enter the key at the secure prompt. It writes the local `bridge.conf`. Do not paste the key into screenshots, tickets, shell history, or logs.
4. In NinjaTrader Control Center, open **New → NinjaScript Editor → AddOns → JournalMeBridge**. Replace the old source with `integrations\ninjatrader\JournalMeBridge.cs`, compile with **F5**, and restart NinjaTrader. Remove an obsolete `JournalMeProbe` if installed. One AddOn installation observes all Control Center accounts; do not install one copy per account.
5. Refresh Connections. Match each detected NinjaTrader connection name and account name to the intended JournalMe trading account, then **Authorize** the two current Lucid accounts separately. Repeat for later accounts. Unknown sources stay pending; verify their identity before authorizing. Confirm per-account snapshots and queue/failure telemetry. Observe capture during the user's next normal trading activity; no test trade is required.
6. Review the first session for duplicates, account assignment, balances, and complete executions. When the new connection is verified and queues are empty, disconnect the stale legacy connector by its short ID. This revokes the screenshot-exposed old key without deleting history. If a new key is exposed, rotate it in the installation card, rerun the helper, and restart NinjaTrader.

If cutover fails, stop the AddOn and preserve both queue files and `bridge.conf` securely. Restore the previous application revisions if needed while retaining the additive schema and the database backup. If the legacy key is still active, return to the old configuration only while flat and with its correct `account_name`. New-installation v2 queue entries remain bound to that installation and must later be replayed through a compatible backend/key; do not reattribute or delete them. If the old key has been revoked, re-pair a legacy connector through the authenticated UI before returning to the old AddOn. Escalate any partial or overlapping trade for manual reconciliation rather than rewriting historical rows.

## Historical gaps

The bridge retries fills it observed and replays only NinjaTrader's [current-session `Account.Executions`](https://ninjatrader.com/fr/support/helpguides/nt8/executions.htm). It cannot prove complete coverage while the PC was off. Compare each account's last bridge contact and fill sync with broker records for the missing dates.

For a CQG-backed Lucid account, [Lucid's setup guide](https://lucidtrading.com/lucid-setup-guide/) says traders sign into Tradovate before using NinjaTrader. Check whether that account can export the Tradovate-style reports the current importer recognizes. Choose the specific existing JournalMe account during preview and inspect detected account IDs, date coverage, warnings, and existing-trade matches before committing. If the detected ID conflicts with the JournalMe account's external ID, stop and resolve the identity mapping; do not edit it just to force an import. Do not infer that platform login grants API access. If the supported Tradovate-style report is unavailable, [NinjaTrader Trade Performance](https://support.ninjatrader.com/s/article/Trade-Performance-Window-NinjaTrader-Desktop?language=en_US) can generate a dated, account-filtered historical execution report and export CSV, but JournalMe needs a validated parser for that format before import. Capture a redacted sample from each relevant provider/export format, including fills around an outage and any overnight position. Automated history requires a verified Lucid-supported export or authorized read-only provider API with stable source IDs and account identity.
